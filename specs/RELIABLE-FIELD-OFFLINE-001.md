# RELIABLE-FIELD-OFFLINE-001

## Простыми словами

Инженер открывает список стройконтроля перед выездом: приложение автоматически сохраняет все его доступные чеклисты, даже если он их никогда не открывал. Список показывает сколько готово. На объекте инженер открывает сохранённый список, отмечает работы, снимает/выбирает фото и видит подтверждение сохранения на устройстве. Интернет и VPN могут отсутствовать независимо. После появления доступа к ФМ очередь доставляется последовательно, без дублей, потери фото и зависшего состояния. Локальная отметка никогда не выдаётся за принятый сервером факт.

## Основание, актор и seams

Прямое поручение26.11.2026 и уточнение «Всегда только мои объекты». Предыдущие наблюдения — external offline-vpn-validation-20261126; это evidence, а не расширение прав. Наследуются YII2-INSPECTION-JOURNEY-001, CHECKLIST-OPERATION-REPLAY-001, INSPECTION-ITEM-COMPLETE-001 и фото/append-only invariants. Этот контракт заменяет прежние противоречащие клиентские ограничения оффлайн-пилота.

Актор — активный инженер с construction_control.read и существующими mutation permissions. Public seams: список/чеклист в браузере и PWA; GET /pilot/construction-control/offline-manifest?page=N; GET /pilot/construction-control/offline; существующие sync-context и checklist mutation endpoints. Серверная авторизация остаётся обязательной для каждой отправки. Новых domain writers нет.

## A1 — Полный набор только своих объектов

Открытие /pilot/construction-control SHALL автоматически запускать подготовку всех объектов с текущим native-закреплением на текущего пользователя, для которых существует доступный checklist read. Видимый ownership=all, поиск и текущая страница не расширяют и не сокращают этот набор. Все страницы набора SHALL быть пройдены; скрытый hard cap недопустим. Включать доступные завершённые объекты только с сохранением действующих read-only правил. Пример: 53 своих и 2 чужих, UI показывает10 строк поиска → сохранены53 своих, чужих0.

Manifest — protected read: positive canonical page, фиксированная порция <=50; JSON {userId,page,pages,total,setVersion,items:[{objectId,checklistUrl,address,registrationNumber,entrance,completed}]}. Гость не получает JSON private data; нет queue permission →403; неизвестные/array/неканонические page →404. GET/HEAD не создают process facts. Сервер формирует собственное назначение, client userId/ownership игнорируются или отклоняются, никогда не расширяют набор. Пустой набор корректно возвращает total0/items[]. Отказ одного документа не превращает весь набор в ready. Все страницы и завершающее повторное чтение первой страницы имеют одинаковый setVersion полного ordered-ID набора. При изменении — максимум3 новых прохода, затем partial с повтором; готовность не заявляется по неполному/чужому набору.

## A2 — Честная подготовка, возврат и PWA

Список SHALL показывать «Готовим для работы без сети: X из Y», «Готово без сети: Y объектов», дату обновления и ошибку/повтор для неполного набора. Готовность засчитывается только после сохранения HTML/данных и необходимых ресурсов, а не получения postMessage. Работать можно до завершения всего набора, но готовность отдельного объекта различима. Загрузка ограничена двумя параллельными документами; повторное открытие возобновляет/обновляет набор, не дублирует queue и не уничтожает неотправленные данные.

Сохранённый список своих объектов SHALL открываться оффлайн с поиском по всем сохранённым объектам, прямыми ссылками на чеклисты и количеством местных изменений. Работают reload, новая вкладка и повторный запуск браузера. /pilot/construction-control и PWA start_url возвращают этот доступный список при отсутствии сервера. Обычная карточка объекта не объявляется доступной оффлайн; возврат из сохранённого checklist ведёт к доступному списку. Manifest PWA имеет стабильные id/start_url/scope, standalone display, подходящие192/512 PNG icons и theme/name; установка использует штатные возможности платформы, без навязчивого автодиалога. При поддержке показывается осмысленное действие установки; Safari получает краткую инструкцию. Если shell уже установлен, но объектов нет, показывается «Сначала подключитесь и подготовьте объекты», без пустого успешного чеклиста. Совершенно первый визит в новый браузер без сети неизбежно остаётся штатной offline-страницей браузера: приложение ещё не загружено.

## A3 — Атомарное местное сохранение

Новая операция, её sequence/зависимость и Blob SHALL сохраняться одной IndexedDB readwrite transaction. «На устройстве» и успешное оптимистическое состояние появляются только после transaction complete. Abort/quota/storage-disabled не создают частичную операцию/осиротевший Blob и не говорят об успехе; показываются понятная причина и восстановление/повтор, данные выбора остаются доступны пока страница жива. Недоступность crypto/storage делает оффлайн-сохранение явно недоступным, не вызывает silent JS failure.

Формат v2 обновляется без удаления существующих operations/photoBlobs/meta/device identity. Каждая очередь изолирована user+device+object. Детерминированный монотонный sequence выделяется атомарно, в том числе при быстрых кликах/нескольких вкладках. Повторный запуск восстанавливает локальные отметки, фото и незавершённые намерения. Старые queued/sending/retryable операции нельзя объявлять неотправленными по догадке: уже существующие wire identities и payload сохраняются, неопределённая отправка повторяется точно.

## A4 — Последовательность, точный replay и несколько вкладок

Все новые обычные и массовые операции одного объекта SHALL образовывать порядок намерений. Пример revision0 → отдельный item28 → отдельный item29 → photo → completion: серверные accepted revisions возрастают без конфликта, вызванного собственными предыдущими операциями. Последующая операция получает базу подтверждённого предшественника только до первой попытки отправки. Photo precedes dependent section completion. Разные объекты не блокируют друг друга.

Перед первым сетевым эффектом точный canonical wire payload SHALL быть сохранён; после неопределённого результата UUID/payload/blob/hash не меняются. Accepted/duplicate подтверждаются только корректным ответом сервера и сохраняются атомарно с receipt/projection. Потеря ответа после commit → тот же запрос → duplicate, один server fact. Серверный conflict настоящей параллельной правки не подавляется автоматической сменой базы. Две вкладки используют exclusive local lease/lock с bounded recovery; серверная идемпотентность — последний предохранитель, не замена локальной последовательности. Открытый старый клиент при upgrade получает понятный запрос обновления без сброса очереди.

## A5 — Интернет, VPN, зависания и авторизация

navigator.onLine SHALL быть только подсказкой; он не запрещает ручной повтор или проверку доступности ФМ. Отправка проверяет fresh sync-context и совпадение server userId с локальной очередью. Auth context содержит actor userId, revision, актуальную projection и CSRF. Отказы содержат стабильный reasonCode (PHOTO_LIMIT_REACHED, PHOTO_INVALID, CSRF_INVALID, ACCESS_DENIED, CASE_NOT_WORKING, STALE_REVISION, OPERATION_PAYLOAD_CONFLICT либо OPERATION_REJECTED), без изменения существующих domain-правил/status. Неподходящая identity никогда не отправляет чужую очередь. 401/403/login redirect/non-JSON auth → «Войдите снова», локальные данные сохранены, процесс не выдаётся за сетевой успех. После входа тем же пользователем исходные wire operations продолжаются с новым CSRF. Отозванные права остаются явным запретом, не меняются клиентом.

Каждый запрос preparation/context/operation имеет bounded timeout <=15сек, photo upload <=30сек; progress не является server receipt. Retryable network/408/429/5xx повторяются с jitter/exponential backoff от2 до60сек, Retry-After ограничивается разумной минутой, есть ручной повтор. Focus/visibility return/online инициируют проверку; при открытом приложении возврат VPN без browser online event возобновляет отправку не позднее следующей попытки <=60сек. Повторы не создают busy loop и останавливаются для auth/deterministic rejection/conflict. Закрытое приложением/ОС окно не обещает отправку в фоне; при следующем открытии работа продолжается. Background Sync — лишь optional acceleration, не обязательная гарантия.

## A6 — Фото, отказ и квота

JPEG/PNG/WebP с камеры/галереи SHALL декодироваться с корректной ориентацией и ограниченными ресурсами. При длинной стороне>2560px или bytes>2.5МиБ готовится читаемая копия с длинной стороной<=2560, целевым размером<=2.5МиБ и hard5МиБ; input hard40МиБ/pixel budget40MP предотвращает неконтролируемую память. Маленький корректный файл разрешено сохранить без изменения bytes. Хэш относится к точным сохраняемым/отправляемым bytes. Неподдерживаемый HEIC/повреждённое изображение получает ясный отказ и выбор другого файла, не исчезает молча. Макс10 active фото/раздел соблюдается локально при конкурентных выборах и сервером.

Pending photo preview восстанавливается после reload. Отказ PHOTO_LIMIT_REACHED/invalid file остаётся видимым с причиной и возможностью скачать локальное фото, удалить локальное намерение либо выбрать замену; бесконечный автоматический retry запрещён. Удаление разрешено только для точно неотправленного/определённо отклонённого намерения, с подтверждением и сохранением server history; sending/uncertain сначала разрешается точным replay. Accepted Blob освобождается только после durable server receipt и сохранения доступного server photo reference; pending/uncertain bytes никогда не очищаются. local export выбранного фото/очереди позволяет сохранить работу до очистки браузера.

Storage estimate/persist используются по feature detection. Отказ persistence не выдаётся за поломку, но готовность объясняет предел браузера. Нехватка места блокирует только новую запись/подготовку с понятным действием; сохранённая очередь не удаляется автоматически. Действие очистки касается только восстанавливаемого кеша после явного выбора, не pending bytes. Очистка пользователем данных сайта/удаление приложения/эвикция ОС принципиально не обещаются как предотвращённые.

## A7 — Конфликт и старая очередь

Conflict/rejected не ретраятся общей кнопкой как network error. Пользователь видит отдельное проблемное действие и свежую серверную проекцию: «Посмотреть изменения», «Применить заново» или «Убрать местное действие». Повтор после сверки создаёт новое явное намерение с новым UUID/свежей базой; исходная попытка/первоначальное device time остаются в местной истории, payload существующего id не переписывается. Зависимые ещё не отправленные действия следуют явному решению; после устранения проблемы очередь возобновляется. Definitive refusal не создаёт server fact. Существующие v2 conflict с двумя offline кликами поддаются этому маршруту; пользователь не должен удалять site data или выполнять JavaScript.

## A8 — Private cache и обновление

Если offline logout оставил серверную cookie, явный маршрут повторного входа SHALL оставаться доступен. POST с введёнными credentials проверяет пароль даже при существующей cookie; ошибочный пароль не выдаёт успешный redirect/подтверждение нового входа. Обычный GET с прежней cookie не снимает локальный tombstone.

Private документы/список принадлежат подтверждённому userId; logout/смена пользователя инвалидируют доступ к прошлому private cache, отменяют pending warmups, но не стирают прошлую queue. Новая сессия не видит/не отправляет чужое. Cross-origin/нечеклист URL не загружаются из manifest. 401/403/auth redirects нельзя маскировать private fallback. Network errors/timeouts/5xx дают last-known-good checklist/list, с видимым возрастом; запрос не зависает перед чтением кеша.

Обновление worker/assets SHALL быть атомарным по generation. Пока новый shell не готов, прежние сохранённые checklist/очередь остаются доступны; upgrade не удаляет последние рабочие private документы только из-за номера версии. Смена account и logout имеют приоритет над опоздавшими ответами. Cached HTML referencing старую версию ресурсов продолжает работать. Cache quota failure не сообщает success. Старые user cache generations не используются для чужой identity.

SHLZ Operate интерфейс на320/390/800/1366px: действия доступны пальцем, нет горизонтального overflow, status aria-live polite, ошибки конкретны, локальное/ожидает/отправляется/принято/требует решения различимы словами. Sync/preparation не блокирует клики/съёмку. Online список, фильтры, планирование инспекций, галерея/отзыв, read-only permissions,85%cap/ПТО и текущая навигация сохраняются. Выход с pending показывает точное количество и последствия, но не удаляет данные. В интерфейс не попадают stack traces/CSRF/SQL/внутренние ревизии.

Тесты MUST воспроизводить real UI+server и durable local evidence: полный mine manifest>50 и чужие; direct offline page без посещения; restart; обычные отдельные клики+фото; uncertain replay; две вкладки; false online flag; VPN blackhole/backoff; expiry/other user; quota transaction abort; >5МиБ/large image; conflict recovery; old v2; worker update/503; PWA. ## Уточнение сохранённых A02/A12 гарантий после полного CI

Наследуется PRODUCTION-PERFORMANCE-001 A02/A12: общий для всех вкладок service-worker scheduler допускает максимум2 спекулятивных document fetch. Публичный `CACHE_CHECKLIST` содержит userId, epoch, worker generation и scope одной попытки подготовки; одинаковые pending/in-flight URL одного подтверждённого actor/epoch/build объединяются, с отдельными подписчиками client+scope. Повтор завершённого запроса в том же client+scope возвращает уже подтверждённый результат; новая попытка получает новый scope и заново читает сервер (не отменяет A2 refresh). Отмена `CANCEL_CHECKLIST_WARMUPS` действует только на scope отправившего client; другой подписчик сохраняет общий запрос. pagehide/новая попытка отменяют старую подготовку и её queued work. Последний отменённый подписчик прерывает fetch. Старый finally не удаляет новую запись с тем же URL. Foreground navigation не ждёт спекулятивных slots; queued speculation ждёт завершения foreground. Перед dispatch/cache commit/result проверяются актуальные actor/epoch/generation. Logout отменяет queued/in-flight work; stale epoch не вызывает новый fetch.

Все ресурсы нового shell, включая content-versioned manifest assets, загружаются явно с cache:no-store и проверкой успешного ответа до публикации generation. Первая установка worker не является обновлением и не показывает update notice; уведомление допустимо только при замене отличающегося подтверждённого поколения, без повторного notice для того же build. Обычная выдача отдельного публичного asset не зависит от наличия полного offline shell. Принятое/пустое синхронизированное состояние сохраняет существующий DOM token `ok`; локальные pending/error/auth/conflict остаются отдельными. Эти уточнения сохраняют ранее установленное поведение и не меняют права/серверные факты.
