# MIKRYUKOVA-FEEDBACK-001

## Простыми словами

Исправляем замечания Ирины Микрюковой одним согласованным пакетом. Монтажников оцениваем по нормативу, предоставленному от фактического начала; премию определяем по остановкам. ОТиЗ управляет резервами и приостановкой выплат, сохраняя суммы других объектов. Источник решений — интервью владельца 24.11.2026, итог подтверждён словом «Делай».

## R1. Каталог

Сводные счётчики и список используют один допустимый кадровый набор (`reconciliation_state=delivered`). Общая численность явно отличается от найденного по пользовательским фильтрам. Непрошедшая сверку запись не увеличивает численность списка. Закрепление и текущая работа независимы: при нуле текущих работ нельзя утверждать отсутствие закрепления. Фильтры, строки, пагинация согласованы, без потери разрешённых назначений. Операция только чтение с существующей авторизацией.

## R2. Остановки и норматив

Положительное целое количество остановок хранится отдельно от этажности, показывается и редактируется существующим авторизованным действием изменения карточки с revision/audit. Премия выбирается по остановкам и существующим типу/грузоподъёмности. Пример: 12 этажей/7 остановок даёт норму для 7 остановок, этажность остаётся 12. Неверное/отсутствующее значение не подменяется этажами в обычном расчёте. Импортёр полностью вне scope; новый атрибут следует существующему контракту source/ручной overlay без нового импорта.

Норматив = разность исходных договорных дат окончания и начала +1 календарный день. Владелец отдельно подтвердил: существующие исходные плановые даты являются договорными; источник workdatestart / plan_finish_date. Даты должны быть валидны, окончание не раньше начала. Допустимое окончание для премии = фактическое начало + норматив -1 день. Пример: договор 01–20.12, факт начала10.12 → норматив20, допустимое окончание29.12. Акт ПТО29.12 →0 дней;31.12 →2 дня, Ксс0,98. При отсутствии ПТО сравниваем дату расчёта. Ксс=max(0;1−0,01×дни просрочки). Текущая справка о переносе задаёт новую допустимую дату вместо вычисленной, без двойного прибавления. Корректировка ПТО и выбор текущей справки сохраняют существующую семантику доказательств. Договорные даты не заменяются фактическими, скорректированной датой или временем загрузки.

Карточка, PDF-шаблон распоряжения, объяснение расчёта и Excel показывают норматив/исходные даты и применённое основание срока там, где выводится срок/расчёт. PDF до открытия показывает предлагаемую дату начала; после принятия оригинала фактическое начало берётся из оригинала. Отсутствующий факт остаётся неизвестным, а не придуманным. Missing/invalid stops/договорный интервал у открытого объекта блокирует финансовое утверждение с понятным объяснением, без выдуманной премии. Прежнее правило допуска не меняется: неоткрытые объекты без фактического начала не входят в forDate/расчёт; карточка показывает отсутствие подтверждённого начала, а не нулевую просрочку.

## R3. Решения, резерв и удержания

OTIZ `otiz.manage` управляет каждой парой объект+монтажник, независимо от текущего закрепления. Обычное исключение сохраняет долю в резерве, не обнуляет право и не раздаёт коллегам. Исходному получателю можно явно выплатить резерв после увольнения. Переход на другой объект не меняет подтверждённый прошлый вклад. Существующий draft→accept→payment workflow распределения сохраняется.

Перераспределение всему оставшемуся допустимому составу исходного расчёта/объекта выполняется по сохранённым положительным весам вклада; исключены исходный получатель, нетрудоустроенные, участники с собственным неразрешённым резервом/приостановкой. При отсутствии допустимых получателей резерв не меняется. Требуются причина, предпросмотр и явное подтверждение. Отсутствуют самопроизвольные новые получатели. Весь остаток нельзя потребить дважды, включая конкурирующие черновики. Повтор operationId идемпотентен, другой payload конфликтует. Права, revision, прямой POST и отказ без частичных записей проверяются владельцем операции.

Автоматическое уменьшение за сроки, дополнительное общее удержание и личное удержание показываются отдельно. Общее уменьшает пул до распределения; личное только выбранную долю. UI не предлагает ввести штраф за уже учтённые сроки повторно. Решения доступны из каждой строки, а не только баннера уволенных.

## R4. Приостановка и частичная выплата

ОТиЗ с `otiz.manage` приостанавливает/возобновляет выплаты по объекту с обязательной причиной/основанием ФКР. Состояние имеет автора, время, revision и неизменяемую историю. ФКР без полномочия ОТиЗ не выполняет денежное действие. Объект должен существовать. Replay не дублирует событие; stale/concurrent mutation отвергается без потери истории. Приостановка действует на все ещё не выполненные выплаты объекта, включая уже утверждённые расчёты и распределения резерва. Начисления/права/резерв сохраняются; hold не является штрафом или report-only фильтром.

При оплате расчёта сервер под тем же object lock проверяет актуальные hold и уже оплаченные обязательства. Можно выплатить остальные объекты. Перед подтверждением UI показывает к выплате сейчас, приостановлено и уже выплачено. Полностью приостановленный расчёт не создаёт нулевой payment. После возобновления выплачивается только остаток. Пример: A6000/B4000, B hold → payment6000 для A, после resume → payment4000 для B; повтор оплаты не создаёт ещё10000. Два конкурирующих запроса не дублируют выплату; replay возвращает прежний результат. Hold/resume и payment сериализованы, а не только проверены в браузере.

Payment detail должен связывать реальные оплаченные обязательства с конкретным payment fact. Сторно отменяет только соответствующий payment subset и восстанавливает его доступность, без изменения соседнего subset. Реестры, экономика, месячные итоги и платёжный Excel используют фактический subset, не полную сумму расчёта для каждого payment. Экспорт/предпросмотр не обходят hold и не отмечают выплату. Исторические обычные факты остаются append-only; исключение R5 относится только к учебной базе.

Разово заполнить остановки из этажности у существующих учебных объектов и обновить учебные расчёты/связанные суммы, включая утверждённые/отмеченные выплаченными, по новым входам. Нельзя оставить старые обязательства/payment суммы/frontiers/reserve расход с новой проекцией. Preview содержит полный inventory затронутых записей/сумм и нерешённых входов. Apply ограничен явным allowlist стенда и точным preview hash/source; одна транзакция/блокировка, идемпотентный повтор и проверка балансов. Missing facts не выдумывать; соответствующие учебные расчёты должны быть явно отмечены/пересозданы согласованно, а не выданы за успешный пересчёт. Не удалять произвольные объекты/пользователей/документы/секреты. Совместимость прежней учебной логики не разрабатывать; fresh schema и штатные обновления должны работать.
