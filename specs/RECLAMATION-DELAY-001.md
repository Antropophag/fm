## Правила
- Дни календарные, целые положительные 1..65535. Номер — строка после trim, 1..255 Unicode символов; не преобразуется в число. Несколько разных номеров суммируются.
- Базовый срок = действующая дата по справке, иначе фактическое начало + договорный норматив (существующая inclusive формула). Итоговый срок = базовый + сумма дней рекламаций. Договорные/плановые даты и первоначальное начало не переписываются.
- Штрафовая просрочка = max(0, дата ПТО либо отчётная дата − итоговый срок). Денежная формула и ограничение Ксобл.срок. остаются в PremiumCalculationV2. Дни рекламаций не начисляют дополнительную премию и не снимают иные удержания.
- На карточке в Сроках и готовности показываются рекламации, сумма дней и итоговая дата для расчёта просрочки; кнопка добавления открывает компактную форму номера/дней. Без отдельного согласования, файла и технических статусов.
- Чтение/добавление используют существующие точные права deadline_certificate.read/write; POST также требует авторизованного доступа к объекту и CSRF. Переданный клиентом caseId не доверяется.
- Единственный application owner EquipmentReclamation\\EquipmentReclamations. add(command) и read(actor,case); currentEvidence(case) для расчётов. Append-only строки, автор/время; actor+request UUID идемпотентен, изменённый повтор конфликтует. Повтор номера в одном деле (trim/lower) отвергается, чтобы не удвоить срок; один номер в другом объекте допустим. Добавление атомарно под блокировкой дела, нет runtimeDDL. Редактирование/удаление этой первой версии не входит в запрос.
- Каноническая additive миграция43. Пустой существующий регистр =0 дней; отсутствие/повреждение регистра — недоступные данные, а не0. Схема проверяет типы/уникальность/FK; повтор миграции безопасен.
- Pure Otiz\\ReclamationDeadline::resolve(normativeDeadline,certificate,evidence) возвращает baseDeadline,baseBasis,reclamationDays,effectiveDeadline,source. Входы/сумма/даты валидируются, proofhash детерминирован.
- Все новые native расчёты и текущий training preview используют единую формулу. Новые draft freshness проверки учитывают hash основания даже при одинаковом Ксобл.срок. Сохранённые snapshots/принятые расчёты/выплаты и exports читают сохранённые значения, не живой регистр. Новое основание применяется только к новому расчёту/явному обновлению черновика; старые деньги не меняются автоматически.
- В Excel сохраняются дни и итоговая дата из snapshot evidence, без liveDB при экспорте. Исторические расчёты без новых полей продолжают читаться. Legacy-active ещё не допущен к текущему native финансовому пути; не создавать новый путь этим изменением.

## Проверки
Root-authored tests: чистая календарная формула/границы, реальный регистр+HTTP/права/CSRF/идемпотентность/дубли, native inputs +0штраф после продления, справка+сумма, неизменяемый опубликованный расчёт, stale draft при том жеКсобл.срок.; saved workbook evidence. Отдельные sol/low исполнители storage/UI и finance. Только bounded проверки; локальную копию схемы обновлять additive после их прохождения.

Сохранение существующих правил: рекламации не отменяют прежнюю обязательность валидного договорного норматива для финансового допуска, даже при наличии справки (mikryukova_inputs_001). Модель доступа к объектам пока глобальная objects.read + точные права действия; отдельную построчную ACL не вводим. Ошибки обычного ввода показываются по-русски с сохранением номера/дней и возможностью повторить ввод.

## Production integration — 26.11.2026
Полная доставка теперь явно разрешена владельцем. Миграция43 совместима только с InnoDB, точными колонками, уникальностью actor/request и case/normalized number, положительными днями и ссылками на case/actor с ON UPDATE RESTRICT и ON DELETE RESTRICT: каскадное изменение/удаление нарушает append-only историю. Отсутствующие/изменённые ограничения дают отказ, не ремонт данных. Deep readiness обнаруживает несовместимость42/43. Backup/restore сохраняет реальные рекламации, номера1С и AUTO_INCREMENT; текущие consumers переходят на43, исторические контракты сохраняются.

Карточка при STORAGE_UNAVAILABLE/EVIDENCE_INVALID либо невозможном итоговом сроке отвечает безопасным503 без технического кода и без новых фактов. FORBIDDEN сохраняет403; отсутствующее право чтения не раскрывает рекламации. Это существующая классификация отказов чтения, применяемая также к новому основанию.
