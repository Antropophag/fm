## Findings

1. **BLOCKING — CLI misclassifies an unknown commit as provider/database unavailability.** `bin/fmonitor2-address-register.php:18` maps `PREVIEW_STALE`, `OPERATION_CONFLICT`, and `PROVIDER_OUTCOME_UNKNOWN` to exit `75`, but omits the application's `COMMIT_OUTCOME_UNKNOWN`. `MariaDbAddressRegisterImportStore::apply` correctly returns `status=unknown, reasonCode=COMMIT_OUTCOME_UNKNOWN` when commit was attempted and reconciliation cannot prove the durable outcome. The CLI therefore falls through to exit `69`, contradicting `specs/ADDRESS-REGISTER-IMPORT-001.md:44`, which requires exit `75` for an unknown commit. This can direct an operator toward provider/database recovery instead of mandatory same-operation reconciliation and risks a blind new operation. **Correction:** include `COMMIT_OUTCOME_UNKNOWN` in the exit-75 classification and add a deterministic CLI regression that forces the existing commit-unknown seam, asserts JSON retains `status=unknown/reasonCode=COMMIT_OUTCOME_UNKNOWN`, asserts exit `75`, and proves no second mutation/new operation is attempted. Recompute the prepared source and rerun the affected focused evidence plus independent final review.

2. **BLOCKING — the supported real package size cannot produce or persist a preview within the shipped runtime/database bounds.** A bounded synthetic probe using the expected source scale of 2,668 rows and 667 unique fake-provider addresses failed after all 667 fake calls. Under the runtime's 256 MiB PHP limit, `AddressRegisterImportApplication.php:851,1169-1188` recursively copies/sorts the complete report and exhausts memory in `json_encode` while computing `previewSha256`. A diagnostic 512 MiB run solely to pass that failure then reached `MariaDbAddressRegisterImportStore.php:53-56` and disconnected MariaDB because the duplicated `source_json`/`report_json` update exceeded the disposable runtime's 16 MiB `max_allowed_packet`. Thus raising PHP memory would not fix the persistence failure. This violates the supported input contract (`specs/ADDRESS-REGISTER-IMPORT-001.md:60` permits up to 20,000 rows) and fails even the known 2,668-row operational source after paid-attempt reservation, leaving no usable reviewed preview. **Correction:** redesign preview hashing and persistence so canonicalization is bounded and the durable package/report representation does not duplicate the full per-field payload into one oversized SQL packet; preserve exact report/replay/restore semantics. Add a deterministic 2,668-row/667-address fake-provider regression under the production 256 MiB runtime and ordinary database packet limit, assert ready preview/report and subsequent restore/replay, and add a bounded limit test that establishes the advertised 20,000-row behavior. Do not treat higher memory or `max_allowed_packet` as the fix. Recompute the verification plan/source and rerun affected focused, architecture, restore, and final review evidence.

No other blocking or non-blocking findings.
