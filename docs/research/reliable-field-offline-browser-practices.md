# Надёжная offline-работа инженера в браузере

Дата проверки источников: 2026-11-26. Область: мобильный браузер/PWA корпоративного FMonitor за VPN, чек-лист и фотографии. Это инженерная записка, а не обещание одинаковой сохранности на любом устройстве.

## Решения

1. **Считать IndexedDB локальным журналом ожидающих операций, а сервер — единственным владельцем подтверждённых фактов.** Операция получает стабильный `clientOperationId`, `deviceInstallationId`, actor/user scope, object/case identity, тип, нормализованный payload, `baseRevision`, device time и состояние `queued/sending/accepted/retryable/rejected/conflict`. `sending` после перезапуска снова считается неопределённым и безопасно повторяется с тем же ID. Сервер на каждом запросе заново проверяет сессию, доступ к объекту, право команды и revision; локально сохранённое право никогда не разрешает запись после reconnect.

2. **Записывать metadata операции и её фото-Blob одной `readwrite` транзакцией IndexedDB и показывать «сохранено на устройстве» только после события `transaction.complete`.** IndexedDB хранит значения через structured clone, который поддерживает `Blob`; спецификация требует атомарно применить все изменения транзакции или откатить их. Успех отдельного `put()` ещё не доказывает commit всей транзакции. Ожидание `complete` даёт правильную прикладную границу, но не абсолютную защиту от внезапной потери питания: durability зависит от браузера/ОС, а транзакции при закрытии страницы вообще нельзя гарантировать. Поэтому запись начинается сразу после выбора/подготовки фото, не в `unload`, и UI удерживает/предупреждает при незавершённой транзакции. [IndexedDB 3.0](https://www.w3.org/TR/IndexedDB/), [MDN: transaction complete](https://developer.mozilla.org/en-US/docs/Web/API/IDBTransaction/complete_event), [MDN: IndexedDB](https://developer.mozilla.org/en-US/docs/Web/API/IndexedDB_API), [MDN: structured clone](https://developer.mozilla.org/en-US/docs/Web/API/Web_Workers_API/Structured_clone_algorithm).

3. **Не обещать, что браузерное хранилище не исчезнет.** IndexedDB и Cache Storage по умолчанию best-effort; пользователь может удалить данные, private/incognito сессия обычно очищает их при завершении, а браузер может удалить origin при нехватке места. Вызывать `navigator.storage.persist()` после понятного пользовательского действия, проверять `persisted()`, показывать результат без ложной гарантии, регулярно брать `estimate()`, ловить `QuotaExceededError` на каждой записи и иметь заранее заданные soft/hard watermarks. На iOS 17+/Safari WebKit у browser origin квота может достигать примерно 60% диска, но это верхняя оценка, а общий лимит и storage pressure всё равно ведут к eviction; WebKit может дать persistence по эвристикам, включая запуск как Home Screen app. Старый Safari также может удалить script-written storage после семи дней использования Safari без взаимодействия с сайтом; Home Screen web app имеет отдельный счётчик взаимодействия. Chromium также сообщает большую теоретическую квоту, но фактическое свободное место не гарантировано. [MDN: quotas and eviction](https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria), [WebKit storage policy](https://webkit.org/blog/14403/updates-to-storage-policy/), [WebKit seven-day policy](https://webkit.org/blog/10218/full-third-party-cookie-blocking-and-more/), [Chrome: storage estimates](https://developer.chrome.com/blog/estimating-available-storage-space/).

4. **Бюджетировать хранилище консервативно.** До выхода в поле экран подготовки обязан сообщить: persistence granted/denied/unknown, приблизительные usage/quota, объём полной очереди и резерв на новые фото. Не начинать съёмку, если безопасный резерв не помещается; предложить синхронизировать/освободить место. Автоматически удалять разрешено только восстановимые cache generations и локальные Blobs уже подтверждённых операций после серверной сверки receipt. Неподтверждённые операции/Blob не вытесняются политикой LRU приложения. Eviction браузера может удалить весь origin, то есть одновременно IndexedDB и Cache Storage, поэтому наличие shell не доказывает наличие очереди и наоборот. [MDN: quotas and eviction](https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria).

5. **Не использовать `navigator.onLine` как допуск или истину о VPN.** Он отражает браузерные/ОС эвристики; LAN может считаться online без доступа к FMonitor, а firewall/VPN может давать ложный offline. События `online`/`offline` — только повод обновить подсказку и запустить ограниченный probe/sync. Реальная доступность определяется authenticated HTTPS-запросом к FMonitor, и только валидный server receipt переводит операцию в `accepted`. [MDN: `navigator.onLine`](https://developer.mozilla.org/en-US/docs/Web/API/Navigator/onLine).

6. **Каждый fetch ограничивать по времени и классифицировать результат.** Использовать `AbortSignal.timeout()` либо совместимый `AbortController` fallback. Для GET/prefetch допустим bounded retry с jittered exponential backoff. Для mutations timeout, abort, network error и потерянный response означают `retryable/unknown`, а не failure или success; повтор идёт с тем же immutable operation ID. `401/403/409/422` не повторять автоматически: требуется login, обновление authority/projection или решение конфликта. `429` уважает `Retry-After`; `5xx` получает ограниченные повторы. Fetch timeout измеряет активное время и может паузиться при suspended document/worker, поэтому дедлайн — защита одного запуска, а не календарный SLA. [MDN: `AbortSignal.timeout()`](https://developer.mozilla.org/en-US/docs/Web/API/AbortSignal/timeout_static), [Chrome Workbox retry behaviour](https://developer.chrome.com/docs/workbox/retrying-requests-when-back-online).

7. **Background Sync считать ускорителем, не механизмом доставки.** API имеет limited availability и отсутствует в Safari/iOS WebKit; браузер ограничивает число повторов и длительность service-worker task. На Chrome/Android событие также планируется браузером и не имеет точного времени. Обязательный путь: sync при открытии/возврате приложения, `pageshow`, успешном reachability probe, пользовательской команде «Отправить» и перед logout/user switch; Background Sync добавляется там, где доступен. Очередь сохраняется в собственном IndexedDB, а не только во внутренней очереди библиотеки. [MDN: Background Sync](https://developer.mozilla.org/en-US/docs/Web/API/Background_Synchronization_API), [MDN: offline/background operation](https://developer.mozilla.org/en-US/docs/Web/Progressive_web_apps/Guides/Offline_and_background_operation), [WebKit open support bug](https://bugs.webkit.org/show_bug.cgi?id=201866).

8. **Гарантировать offline start через законченный generation-scoped shell.** В install загружать минимальные HTML fallback/app shell, CSS, JS, icons и offline route в новый cache generation; install успешен только если обязательный набор целиком сохранён. Fetch навигации контролируется только для канонических checklist routes. Private checklist data хранится user/device/object scoped в IndexedDB или user-bound cache и никогда не попадает в общий публичный shell. При обновлении сохранять старую generation, пока новая полностью не установлена; удалять только уже не используемые старые recoverable caches после проверки зависимостей документов/клиентов. Принудительные `skipWaiting()`/`clients.claim()` безопасны только при совместимых schema/protocol или после завершённой миграции: иначе новая worker-логика может управлять старой открытой страницей. Cache identity включает build/content generation и пользовательский scope; install fetches обходят HTTP cache (`cache: no-store`). [MDN: service-worker lifecycle](https://developer.mozilla.org/en-US/docs/Web/API/Service_Worker_API/Using_Service_Workers), [MDN: PWA caching](https://developer.mozilla.org/en-US/docs/Web/Progressive_web_apps/Guides/Caching), [web.dev: offline assets](https://web.dev/learn/pwa/assets-and-data/).

9. **Автоматически предзагружать только полный текущий набор «Мои объекты» инженера, а не текущую страницу или общий читаемый список.** Источник — каноническое native-assignment текущего actor: prefetch включает его собственные назначенные checklist objects на всех страницах и никогда не включает объекты коллег лишь потому, что actor может читать их через общий поиск, фильтр `All`, административное или иное read-полномочие. После успешной загрузки очереди «Мои объекты» клиент проходит её официальный cursor/next pagination endpoint до конца в рамках одного `prefetchGeneration`, сохраняет checklist snapshot каждого собственного назначенного объекта и manifest `{actor, device, generation, fetchedAt, objectIds, cursorsComplete}`. Переход в состояние «готово к работе offline» возможен только при достигнутом конце пагинации, успешном commit всех документов и shell, отсутствии ошибок/пропусков и достаточном storage reserve. Пользователь не должен вручную открывать detail pages. Возможны bounded batch payload либо фоновый GET существующих авторизованных HTML-документов с тем же native-assignment scope; это не browser navigation. В FMonitor выбран второй вариант с manifest и concurrency2, чтобы использовать существующий renderer и его авторизацию без отдельной модели формы. Дедупликация URL/object, максимум два фоновых fetch, приоритет foreground, отмена на pagehide/logout/user switch/new generation соответствуют уже принятой FMonitor границе `PRODUCTION-PERFORMANCE-001`.

10. **Prefetch не закрепляет авторизацию.** Offline UI показывает последнюю серверную выборку как датированный snapshot и разрешает создавать локально ожидающую операцию только в actor/device/object scope того snapshot. После reconnect сначала обновляется сессия и текущее native-assignment; затем каждая команда отправляется в канонический server seam, который заново проверяет actor, object read/command access, assignment, current revision и immutable operation identity. Отозванное право даёт `rejected`, изменившееся состояние — `conflict`; локальная запись и Blob сохраняются для объяснения/экспорта уполномоченному пользователю, но не становятся серверным фактом. Новые собственные объекты добавляются только после появления в текущем native-assigned наборе actor при следующем полном обходе пагинации «Мои объекты»; снятые с него объекты помечаются stale и перестают принимать новые локальные команды после успешного refresh. Объекты коллег не добавляются по одному read-доступу.

11. **Фото декодировать и уменьшать до постановки в очередь, сохраняя проверяемую ориентацию.** Сразу хранить оригинальные metadata (name, MIME, size, capture/device time), затем декодировать через `createImageBitmap(blob, {imageOrientation: "from-image"})` там, где поведение проверено; fallback через `HTMLImageElement`/canvas должен быть device-tested на EXIF 1–8. Рассчитывать размеры с ограничением максимальной стороны без upscale, рисовать в canvas/OffscreenCanvas, экспортировать bounded JPEG/WebP, затем вычислять SHA-256 именно передаваемых bytes. Не полагаться на предположение, что все browser decoders одинаково применят EXIF: тестовый набор обязан покрывать повороты и отражения, iOS HEIC/unsupported decode, extreme dimensions, memory pressure и отсутствие `createImageBitmap`. До удаления исходного Blob новая производная должна атомарно попасть в IndexedDB вместе с metadata; при decode/encode/quota failure исходник не теряется и операция не объявляется готовой. [MDN: `createImageBitmap`](https://developer.mozilla.org/en-US/docs/Web/API/Window/createImageBitmap), [MDN: canvas image scaling](https://developer.mozilla.org/en-US/docs/Web/API/Canvas_API/Tutorial/Using_images).

## Пользовательский контракт подготовки к выезду

Экран должен иметь явную команду «Подготовить все мои объекты для работы без связи» и автоматически продолжать тот же процесс при открытии очереди на надёжной сети. «Все мои» всегда означает полный native-assigned набор текущего инженера через все страницы; выбор `All`, общий поиск и read-доступ к объектам коллег не расширяют prefetch. Итог показывает число объектов, время snapshot, занятое место, persistence status и три честных состояния: «готово полностью», «готово частично — перечислены объекты/причины», «не готово». Наличие PWA на домашнем экране, service worker или зелёного `navigator.onLine` само по себе не считается готовностью.

Перед выездом выполняется реальный airplane-mode/VPN-off probe: приложение запускается с закрытого состояния, показывает полный manifest, открывает каждый checklist без detail pre-open, создаёт item operation и фото, переживает reload/restart, затем после VPN reconnect получает accepted/duplicate receipts. Отдельно проверяются iPhone Safari/Home Screen и поддерживаемая Android Chrome PWA на минимальном допустимом объёме свободного места. Не проверенные комбинации устройства/OS/browser/storage остаются `UNKNOWN`.

## Минимальная матрица отказов

- обрыв до IndexedDB commit и сразу после него;
- закрытие вкладки/убийство PWA во время resize, commit, upload и ожидания response;
- quota exhaustion, denied persistence, browser eviction и ручная очистка site data;
- VPN подключён без маршрута к FMonitor, captive portal, медленный ответ, DNS/TLS failure;
- потерянный accepted response и точный replay; concurrent replay с другого tab;
- logout/user switch и поздний prefetch response старого пользователя;
- revoke assignment/role между prefetch и sync; server revision conflict;
- pagination error/loop/duplicate/cursor drift и объект, появившийся во время обхода;
- обновление service worker при открытой старой странице и миграция IndexedDB schema;
- EXIF 1–8, HEIC/unsupported file, huge raster, corrupted image и low-memory kill.

## Практический предел обещания

Обычный web/PWA не может дать абсолютную гарантию сохранности неподтверждённых данных: устройство может быть потеряно, пользователь может очистить site data, ОС может удалить данные, старый Safari — применить proactive eviction, а питание может исчезнуть до физической записи. Реалистичный контракт: минимизировать окно потери атомарной немедленной записью, запросить persistence, контролировать quota, никогда не удалять pending evidence автоматически, явно показывать локальный/серверный статус и как можно скорее получать идемпотентный server receipt. Для требования «данные не теряются ни при каких условиях» нужен управляемый native-клиент/MDM и отдельная аппаратно-операционная гарантия, которой браузерные стандарты не дают.
